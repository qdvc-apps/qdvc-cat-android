### On the "where am I in the document?" question (discussion only)

Good instinct that a desktop-style scrollbar would feel out of place. A few Android-idiomatic options, roughly in order of how native they feel:

**Fast-scroll thumb (most idiomatic).** The standard Android pattern for long lists is a draggable scroll thumb that only appears while scrolling and fades out after a moment — plus often a "position bubble" showing where you are (e.g. a line number or percentage). This is exactly what the AOSP `RecyclerView` fast-scroller and apps like Google Files do. In Compose you'd derive position from the `LazyListState` (`firstVisibleItemIndex` / total items) and draw a thin thumb overlay on the right edge, shown only during/just after scrolling. It's lightweight (no extra layout of content), discoverable, and lets users jump quickly. This would be my default recommendation.

**Position indicator / percentage in the top bar.** Even simpler: show "line 1,240 / 8,003 (15%)" in the app bar subtitle, updating as you scroll. Zero new gestures, near-zero cost, and it directly answers "where am I". Pairs well with the fast-scroll thumb.

**A VS Code-style minimap.** Feasible, and it can look great, but it's the least Android-idiomatic of the three and the one with real performance/appropriateness caveats:
- *Rendering cost.* A true minimap renders the whole document in miniature. For an 8 MB file that's far too much to lay out as text. The practical approach is to render it as a **cached bitmap** drawn once (colored horizontal ticks per line, using the same token colors — you already have the highlighter), then just overlay a moving "viewport" rectangle. Regenerate only on file load, theme change, or width change. Done that way it's cheap at scroll time.
- *Fidelity vs. lazy tokenising.* Your highlighter is deliberately lazy (only visible lines are tokenised). A full minimap would force at least a coarse tokenising pass over the whole file to color it — which conflicts a bit with the lazy design. You could downsample (e.g. one tick per N lines, colored by that line's dominant token) to keep it bounded.
- *Screen real estate.* On a ~360 dp-wide phone, a 1 cm strip is a meaningful chunk of width; it competes with the text. It shines on tablets/landscape and feels cramped on a phone. A reasonable compromise is to make it optional (a settings toggle) or only show it in landscape/wide layouts.

My suggestion if you want to pursue this: start with the **fast-scroll thumb + a line/percentage indicator** (high value, very idiomatic, cheap), and treat the minimap as an optional, tablet-oriented extra built on a cached bitmap with downsampling — only if you decide the extra polish is worth the added complexity. Happy to spec any of these out or implement when you'd like.
